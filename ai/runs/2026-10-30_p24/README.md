## 재현

모델은 Hugging Face의 ONNX export를 미리 받아 `<models-root>/<owner>--<name>/`에 둔다(가중치·캐시는 커밋하지 않음). 실행 환경(2026-11-01 재실행): Python 3.12.3, onnxruntime 1.31.1, tokenizers 0.23.3, numpy 2.5.4, 그 밖의 서버 패키지는 `backend/uv.lock` 그대로(`uv export --frozen --no-dev`, M3a 층 import에 pydantic 등이 필요), CPU Intel Xeon 2.10GHz(AVX-512 VNNI) 4코어 중 `--threads 2`(2 vCPU 서버 가정), RAM 16 GB. torch는 쓰지 않는다. 모델 파일은 `huggingface_hub.hf_hub_download(repo, file, revision=<아래 표>, local_dir=<models-root>/<owner>--<name>)`로 `onnx/<파일>`(+`_data`)과 `tokenizer.json`을 받았다.

```
python ai/eval/p24_embedding_compare.py run --model tfidf --out ai/runs/2026-10-30_p24
for m in minilm-l12 e5-small e5-small-int8 e5-base e5-base-int8 bge-m3; do
  python ai/eval/p24_embedding_compare.py run --model $m --models-root <models-root> --threads 2 --out ai/runs/2026-10-30_p24
done
python ai/eval/p24_embedding_compare.py summary --out ai/runs/2026-10-30_p24
```

모델은 프로세스 하나에 하나씩 돌린다(메모리 숫자를 깨끗하게). `run`은 하네스나 입력(`ai/eval`, `ai/catalog`, `eval`, 서버 매칭 코드)에 미커밋 변경이 있으면 멈추고(`--allow-dirty`로만 진행), 커밋·미커밋 변경·하네스 SHA-256을 `provenance`에 남긴다. `provenance.model`에는 선언한 Hugging Face 저장소·revision과 함께 실제로 읽은 파일(ONNX, 있으면 `.onnx_data`, `tokenizer.json`)의 SHA-256과 크기가 들어간다(메모리를 잰 뒤 조각으로 읽어 해시). `summary`는 모든 `model_*.json`의 카탈로그 파일·정답·라벨 SHA-256, 바별 카탈로그 digest, 카탈로그 변형·문서 집합·정책·M3a 정책 목록, 하네스 SHA-256, 규칙 기준선(서버 매칭 코드는 해시하지 않으므로 그 대신)이 모두 같지 않으면 0이 아닌 코드로 멈추고 다른 필드를 적는다. 커밋은 비교하지 않는다(하네스와 입력이 같으면 숫자가 같다). 대신 모델별 커밋·미커밋 변경·모델 파일을 `summary.json` `runs`에 남긴다.

**어느 커밋의 결과인가.** `model_*.json` 7개 모두 `bb526f8`에서 깨끗한 상태(`provenance.uncommitted_changes = []`, `--allow-dirty` 없음)로 위 명령 그대로, 한 프로세스에 모델 하나씩 차례로 돌린 값이다. `summary.json`은 새 일관성 검사를 통과했다. 결과를 담은 커밋은 그다음 커밋이다(결과 파일은 실행 뒤에 커밋하므로 실행 커밋은 언제나 결과 커밋의 부모다. `ai/runs`는 `provenance` 검사 경로가 아니다).

직전 결과(`8605400`에서 실행, 결과 커밋 `a04851e`)와 비교하면 `catalogs` 전체(recall·정책 5종 지표·확인 권장 보정·`unmatched_top`과 하한 스윕·불변식)와 M3a 조합의 부담·확인 권장 지표는 7개 모두 같다. 달라진 것은 ① `M3a_then_embedding` recall: 예전에는 M3a 결과에 임베딩 순위를 이어 붙인 목록으로 세어, M3a가 ambiguous로 남겨 임베딩 후보가 붙지 않는 줄까지 셌다. 이제는 결과마다 화면에 보이는 `candidates`로 센다(결과 3) ② M3a 조합을 권장 정책 `unmatched_k5+rerank_only`로도 돌렸다(`llm.<카탈로그>.policies`) ③ `provenance.model` ④ 지연·임베딩 시간·메모리(같은 컨테이너에서 다시 잼, 아래). 그 앞의 이력: 처음 6개 모델 결과는 하네스가 커밋되기 전(`c976b4f` + 미커밋 하네스)에 돌아 `floor_sweep`이 `null`이었고, `8605400`에서 다시 돌렸을 때 recall·보정·M3a 조합·불변식, 그리고 처음에 있던 정책 4종 지표는 처음 값과 같았다. | 조건 | 카탈로그 | 뜻 |

| — | `service` | 서비스 카탈로그 그대로. 결과가 `eval_p17`과 줄 단위로 같다(괄호제거 별칭 265개는 S1의 괄호 변형이 이미 처리) |

| (3) 규칙 + 임베딩 후보 | 위 카탈로그 각각 | 규칙 결과 위에 `apply_policy`로 임베딩 후보를 붙임. 확정된 줄은 그대로, 새로 만드는 결과는 언제나 `ambiguous` |

문서 집합(무엇을 임베딩하나): `canonical` 표시명, `aliases` 표시명+별칭 전부, `korean` 한글 별칭만, `brand_age` 표시명+"브랜드 별칭 에디션 연수(년)", `all` aliases+brand_age. 상품 점수는 그 상품 텍스트들 중 최고 코사인.

정책: `unmatched_k5`/`k3` 규칙이 못 찾은 줄(unmatched)에만 상위 5/3개, `fill_k5` 후보가 있는 ambiguous 줄(확인 권장 없음)에도 5개까지 채움, `rerank_k5` fill + 임베딩 순서로 재정렬, `unmatched_k5+rerank_only` unmatched에 5개 + ambiguous 줄은 추가 없이 임베딩 순서로 재정렬만. 확인 권장(confirmRecommended)은 어떤 정책도 달지 않는다.

## 하지 않은 것 / 주의

- dev 5곳만. 숫자 대부분(특히 하한·임계값)은 같은 데이터에서 본 것이라 낙관적이다. 채택 판정은 I3 동결 시험셋에서 따로 해야 한다.

- 지연은 이 컨테이너 CPU(Xeon 2.10GHz, AVX-512 VNNI) 2스레드 값이다. 운영 서버 t3.micro(2 vCPU 버스터블, 1 GiB)에서는 더 느릴 수 있고 거기서 재지 않았다. TF-IDF 지연은 순수 Python 희소 구현 값이다.
- 하네스는 `i3_match_eval.dev_photos()`만 쓴다(I3 파일이면 거부). 실행 중 `ai/docs/i3_eval_freeze.md`의 한 줄(E10 도구 설명, 230행)이 레포 전체 grep 결과에 섞여 보였다. 바 이름·라벨·정답은 보지 않았다.
