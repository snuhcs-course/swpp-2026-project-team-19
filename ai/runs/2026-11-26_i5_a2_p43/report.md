## 1. A2: 계정당 하루 사진 한도

커밋 `828a03d4`.

- I4-A6의 하루 한도 장치(`app/services/request_limits.py`)에 종류 하나(`menu_import_photos`)를 더했다. 새 장치는 만들지 않았다.
- **접수한 사진 수로 센다.** `POST /api/bars/{barId}/menu-imports`가 `202`로 접수될 때 그 요청의 사진 수만큼 한 번 센다.
- 세지 않는 것: 같은 키의 재요청, 다른 검사(`413`, `415`, `409` 등)에서 거절된 요청, 서버 재시작 뒤 복구로 다시 처리되는 사진, 추출이 다른 경로로 내려가 다시 읽는 사진.
- 접수한 뒤 저장이나 DB 기록에 실패하면 센 수를 되돌린다.
- 추출 경로와 무관하다. `MENU_EXTRACTOR`가 `mock`, `gemini`, `openrouter` 어느 것이든 같은 한도다.
- 한도를 넘으면 `429 RATE_LIMITED`(스펙에 이미 있는 코드)로 요청 전체를 거절하고 아무것도 저장하지 않는다.
- operator 초기화 API(`POST /api/request-limits/reset`)가 `kind = menu_import_photos`를 받는다. 운영자 대시보드의 초기화 화면에도 "메뉴 사진 등록" 선택지를 넣었다.

```json
{
  "error": {
    "code": "RATE_LIMITED",
    "message": "오늘 올릴 수 있는 메뉴 사진은 5장 남았습니다. 사진을 5장 이하로 줄이거나 내일 다시 시도해 주세요.",
    "details": {"retryAfter": "2026-11-26T15:00:00Z", "dailyLimit": 30, "remaining": 5, "requested": 8},
    "fieldErrors": []
  }
}
```

**알아 둘 한계**

- **PDF는 아직 업로드 API가 받지 않는다.** "PDF는 페이지 수로 센다"는 세는 함수(`acquire_menu_photos`)가 사진 수를 받는 것으로 준비했고 테스트도 그 수준이다. PDF 업로드를 붙일 때 페이지 수를 넘기면 된다.
- **서버가 재시작되면 그날 센 수가 지워진다.** 기존 한도(진위확인, OCR)와 같은 방식이고 스펙 3.11.14가 받아들인 한계다. 배포를 하면 모든 계정이 다시 30장을 쓸 수 있다.
- 임시 로그인 토큰은 `sub`가 모두 같아서 한도 하나를 같이 쓴다(로컬 개발 전용).

**테스트** (`backend/tests/test_menu_photo_limit.py`, 27개, DB 없이 실행)

| 지시 문서의 항목 | 테스트 |
|---|---|
| 한도 직전 | 15장 + 15장으로 정확히 30장까지 접수, 1장 더는 거절 |
| 초과 | 25장 쓴 뒤 8장: 전부 거절, `remaining = 5`, 저장 0건. 이어서 5장은 접수 |
| 날짜가 바뀐 뒤 | KST 자정 1초 전에 거절, 자정에 다시 접수 |
| 운영자 초기화 | 한 사용자·한 종류만 지움, 다른 종류는 그대로, 지운 뒤 다시 접수 |
| PDF 페이지 | 12쪽 PDF 두 번에 24장, 세 번째는 `remaining = 6`으로 거절 |
| 재시작 복구 | 등록 처리·복구 코드가 한도 장치를 쓰지 않는 것을 확인 (아래 한계 참고) |
| 그 밖 | 재요청은 다시 세지 않음, 저장 실패 시 되돌림, 삽입 경쟁에서 진 요청은 세지 않음, 설정값 오류는 서버 시작 실패, 라우트의 `429` 본문 |

- **이 PC에는 테스트용 PostgreSQL이 없어서 DB를 쓰는 API 테스트는 돌리지 못했다.** 그래서 A2 테스트는 가짜 세션 위에서 업로드 함수와 라우트를 직접 부른다. "재시작 복구"는 실제 복구를 돌려 본 것이 아니라 코드 구조로 확인한 것이다.
- 기존 DB 테스트가 새 한도에 걸리지 않게 `tests/conftest.py`에서 테스트 중 한도를 100만 장으로 둔다. 한도 장치가 프로세스에 하나고 임시 로그인 토큰의 `sub`가 같아서, 그대로 두면 테스트 전체의 업로드가 합쳐져 30장을 넘는다. **이 부분과 기존 업로드 API 테스트는 CI에서 확인해야 한다.**

## 2. P43: 동시 실행

커밋은 이 보고서와 같은 커밋이다.

**코드로 확인한 것**

- **한 등록 안에서는 사진을 순서대로 한 장씩 읽는다** (`menu_import_processing._extract_all`의 `for image in menu_import.images`). 스펙 4.1에도 그렇게 적혀 있다.
- **등록끼리는 동시에 돈다.** 등록 처리(`process_menu_import`)는 동기 함수이고 FastAPI의 `BackgroundTasks`로 실행되므로 Starlette가 스레드 풀에서 돌린다. 등록마다 스레드 하나를 쓴다.
- 추출기는 프로세스에 하나다. 여러 등록이 같은 추출기와 같은 차단기를 쓴다. 차단기는 잠금으로 보호된다.
- 스레드 풀의 기본 크기는 40이다. 처리 중인 등록 하나가 끝날 때까지 스레드 하나를 잡고 있으므로, 동시에 처리 중인 등록이 40개에 가까워지면 다른 API 요청도 기다리게 된다. 알파 테스트 규모에서는 닿지 않는다.

**15장 한 번 등록의 예상 시간** (추출만, 사진을 순서대로 읽으므로 15배)

| 사진 1장 | 15장 |
|---|---|
| 중앙값 28초 | 약 7분 (420초) |
| p95 71초 | 약 17분 45초 (1,065초). 15장이 모두 느린 경우의 상한이다 |

- 28초와 71초는 11/21 회귀 17장 3회 측정값이다(보고서 9.6절). 11/25 서버 코드 경로 1회는 중앙값 35.1초, p95 55.9초였고, 이 값으로는 약 8분 47초와 약 14분이다.
- 여기에 사진마다 OCR 약 1초와 마지막 매칭 시간이 더해진다. 호출이 재시도되면 더 길어진다(11/25에 한 장이 283초 걸렸다).

**가짜 응답 테스트** (`backend/tests/test_extraction_concurrency.py`, 4개, 5회 반복 실행해 모두 통과)

- 등록 3개의 모델 호출이 동시에 진행 중인 상태가 된다(세 호출이 모두 들어와야 풀리는 장벽으로 확인).
- 한 등록의 느린 사진이 다른 등록의 사진을 막지 않는다.
- 등록 3개가 동시에 실패하면 차단기가 한 번 열리고 셋 다 2단계로 내려간다.

**실제 OpenRouter 동시 호출** (11/26, 진우 승인 뒤, `ai/eval/i5_concurrent_imports_check.py`)

등록 3건을 스레드 3개로 동시에 돌렸다. 등록마다 사진 2장을 순서대로 읽고, 세 등록이 차단기 하나를 같이 쓴다. 사진은 서버 추출 함수(`extract_menu_routed`)를 거친다.

- **세 등록이 서로 막지 않았다.** 호출 6회의 시간 합은 144.8초인데 전체는 69.7초에 끝났다. 동시에 진행 중이던 호출은 최대 3개다.
- 등록 A는 30.4초, B는 44.7초, C는 69.7초에 끝났다. 각 등록의 시간은 자기 사진 2장의 합과 같다.
- 사진 1장의 시간은 11/25에 한 장씩 돌렸을 때와 비슷하다(15~39초 대 17~36초). 동시에 돌려서 느려졌다고 볼 차이는 없다. 사진마다 1회라서 그 이상은 말할 수 없다.
- 6장 135칸 모두 맞음, 틀린 가격 0. 6장 모두 0단계(3.8 Flash)로 읽혔고 재시도와 잘린 시도는 0건이다.
- 쓴 비용 $0.125 (상한 $1).
- **배포 설정과 다른 점:** 대체 모델 없이 3.8 Flash만 불렀고 Gemini 직접 경로는 닫았다(2단계 회귀 실행과 같다). 그리고 상한 $1을 보장하려고 출력 상한을 48,000이 아니라 16,000으로 뒀다. 6장의 출력은 2,700~5,800 토큰이라 결과에는 영향이 없다.
- 동시 3건, 사진 2장씩, 1회다. OpenRouter나 제공자의 요청 수 제한에 걸리는 규모는 확인하지 않았다.

**확인하지 못한 것**

- DB까지 포함한 등록 3개의 동시 처리. 이 PC에 테스트용 DB가 없다. 가짜 응답 테스트와 실제 호출 모두 추출기 수준이다.
