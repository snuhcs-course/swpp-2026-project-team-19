## 근거 표

규칙(1)과 규칙+P17 생성 한글 별칭(2): Top-1 0.643 → **0.771**, FM 0 → 0, 어려운 줄/사진 8.10 → 4.59. 생성 별칭이 효과의 대부분이다(괄호제거 별칭은 결과 변화 0).

(3) 규칙+임베딩, 서비스 카탈로그. recall은 문서 집합 `aliases`(표시명+별칭)로, 규칙이 확정 못한 알려진 184줄의 @1 / @5다. **지연은 문서 집합 `all`(별칭+브랜드·연수 문자열) 인덱스**로 잰 사진당(평균 28.8줄) CPU 2스레드 값이고, **메모리는 실행 전체**(문서 집합 5종, 카탈로그 4종을 모두 임베딩한 프로세스)의 값이다. 별칭만 쓰는 서버 인덱스는 텍스트가 더 적으므로 둘 다 이보다 조금 작을 것이다(재지 않음). 지연·메모리는 일곱 개를 같은 컨테이너 CPU(Xeon 2.10GHz, AVX-512 VNNI)에서 `bb526f8`로 차례로 다시 잰 값이고(2026-11-01), 처음 값보다 지연이 절반쯤 작다. 직전 `8605400` 실행보다는 지연 평균이 8~26% 길고 메모리는 1% 안에서 같다(둘 다 README). 지연은 실행마다 이만큼 흔들린다:

보이는 목록은 모든 임베더가 권장 정책(`unmatched_k5+rerank_only`) 값이다. 처음 메모는 이 정책을 TF-IDF와 e5-small int8만 돌려 나머지는 재정렬 없는 `unmatched_k5` 값(MiniLM 0.71 / 0.84, e5-small fp32·e5-base int8·bge-m3 0.84 / 0.95)을 적었다.

² 바 인덱스마다 그 바 카탈로그 텍스트로만 fit해서 다시 돌린 값(`32b8314`, 아래 "리뷰 반영"). 처음 값(0.71 / 0.96, 0.42 / 0.72 s)은 모든 바의 텍스트로 IDF를 fit해 바 자신의 메뉴 표기가 가중치에 섞였다.
³ 모델 로드 증가 0. 최고 RSS는 하네스가 바 인덱스 100개(카탈로그 4 × 문서 집합 5 × 바 5)를 동시에 들고 있는 값이라 인덱스 하나인 서버와 다르다.

- 생성 별칭이 **없는** 카탈로그(eval)에서는 bge-m3만 강하다(@1 0.84, e5-small int8 0.70, TF-IDF 0.33). 생성 별칭이 있으면 차이가 사라진다. 서비스는 생성 별칭을 쓰므로 bge-m3의 이점은 우리 조건에서 거의 없다.
- 업주 부담(서비스): register 71 → 0, 알려진 줄 직접 등록 45 → 0, choose 53 → 107, wrong 9 → 26(정답 상품이 없는 26줄도 후보를 받음). 어려운 줄 수 자체는 같고, "검색해서 등록"이 "목록에서 고르기"로 바뀐다.
- 후보가 하나인 ambiguous 줄에 후보를 더하면 confirm이 choose로 바뀐다(85 → 46). 추가는 unmatched 줄에만.
- 점수만으로 확인 권장: 유사도 ≥ 0.93이 서비스 카탈로그에선 36줄 중 35 정답, 그 바 상품을 뺀 카탈로그에선 72줄 중 22 정답. 없는 술이면 형제 상품이 높은 점수로 1순위가 된다.
- M3a 뒤에 임베딩(M3a가 못 찾은 줄만 채움): 확인 권장 변화 없음. 보이는 목록 @1 / @5(e5-small int8, 서비스)는 M3a만 0.82 / 0.88에서 `unmatched_k5` 0.91 / 0.97, 권장 정책 `unmatched_k5+rerank_only` **0.94 / 0.98**(TF-IDF 0.90 / 0.97, 0.92 / 0.98). 처음 메모의 "0.88 → 0.98"은 M3a가 ambiguous로 남긴 줄에도 임베딩 순위를 이어 붙여 센 값이었고(보이지 않는 후보 포함), 이제 화면에 보이는 후보로 센다. 다만 생성 별칭이 없는 eval 카탈로그에서는 재정렬이 @1을 내린다(e5-small int8 0.83 → 0.81, TF-IDF 0.81 → 0.79; LLM 순서가 더 나음). M3a 앞에 임베딩(LLM의 새 선택은 임베딩 후보 안에 있어야 확인 권장): 틀린 확인 권장 14 → 13(dropprod)이지만 eval에서 정답 확인 권장 30개 손실. 부담·확인 권장 숫자는 두 정책에서 같다(재정렬은 순서만 바꿈).

## 추천

1. **1단계는 EC2 안에서 TF-IDF, e5-small int8은 서버를 `t3.small` 이상으로 늘리거나 별도 CPU 서버로 뺀 뒤.** 운영 서버는 AWS `t3.micro`(2 vCPU 버스터블, RAM 1 GiB, API 프로세스 하나)로 확인됐다.
   - **1단계(지금)**: API 프로세스 안에 문자 1~3-gram TF-IDF 인덱스. 모델 파일·추가 패키지가 없고 모델 로드 메모리 증가가 0이다(하네스 최고 RSS 1048 MB는 바 인덱스 100개를 동시에 든 값이고, 서버의 인덱스 하나는 재지 않았다. 텍스트 수천 개의 희소 벡터라 수십 MB 이하일 것으로 본다). 보이는 목록 @5 0.95로 e5 int8(0.96)과 거의 같고 register 71 → 0, 알려진 줄 직접 등록 45 → 0도 같다. 손해는 @1이 0.83 대 0.91인 것(정답이 1순위가 아니고 2~5순위인 줄이 약 15줄 많음)이다.
   - **2단계**: `intfloat/multilingual-e5-small`의 int8 ONNX export (`onnx/model_qint8_avx512_vnni.onnx`, revision `614241f6`), onnxruntime + tokenizers + numpy, torch 없음. 품질은 fp32·bge-m3와 같고(임베딩 순위 @1 0.93, 보이는 목록 0.91 / 0.96) 일곱 개 중 지연·메모리·파일이 가장 작다. 그래도 모델을 올리면 프로세스 RSS가 **+452 MB**, 하네스 실행 최고 **697 MB**(처음 측정 453 / 694 MB, `8605400` 460 / 706 MB)다. 1 GiB에서 OS와 API 프로세스(FastAPI·SQLAlchemy·boto3·google-genai)를 빼면 이만큼 들어갈 자리가 없다. `backend/DEPLOY.md`(60~64행, "A small instance needs swap for `uv sync`")대로 서버에 1 GB 스왑 파일이 있지만, 스왑은 디스크(EBS)라 느려서 메모리가 모자랄 때 OOM을 늦추는 대비일 뿐 모델을 상주시킬 자리가 아니다. 모델 페이지가 스왑으로 밀리면 메뉴 업로드마다 디스크를 읽어 느려지고, 업로드가 몰리면 결국 OOM으로 API 자체가 죽을 수 있다. 지연은 이 CPU에서 사진당 0.13 / 0.26 s(평균 / p95)로 TF-IDF(0.15 / 0.32 s, 순수 Python)와 비슷해 문제가 아니지만, 시작·카탈로그 변경 때 텍스트 5,382개 임베딩에 10.3 s CPU를 쓰고 추론도 CPU를 꽉 쓰므로 t3.micro의 CPU 크레딧(기준 성능 vCPU당 10%)을 API 요청과 나눠 쓰게 된다. 그래서 서버를 `t3.small`(2 GiB) 이상으로 늘리거나, 임베딩만 따로 도는 CPU 서버(같은 어댑터 뒤 HTTP)로 뺀 뒤 켠다.
   - 어댑터가 같으므로 1단계 → 2단계 교체는 설정(`EMBEDDING_MODEL`)과 모델 파일 배포다. 하한은 모델마다 척도가 달라(아래 4) 같이 바꾼다.
2. **임베딩할 것: 상품 표시명 + 활성 별칭 원문 전부(생성 한글 표기 포함)**, 상품 점수는 최고값. 브랜드+연수 문자열은 생성 별칭이 있을 때 이득이 없어 뺀다(별칭이 없는 신규 상품을 위해 나중에 다시 볼 것).
3. **저장: 프로세스 메모리**. 텍스트 약 4,500개 × 384차원 float32 ≈ 7 MB, 전체 내적 1회 < 1 ms. pgvector는 RDS 확장·마이그레이션·백필이 필요한데 이 규모에선 얻는 것이 없다(상품 수만 개 이상이면 재검토).
4. **정책**: 규칙(+M3a)이 unmatched로 남긴 줄에만 상위 5개를 `method="embedding"`으로 붙이고, 확인 권장이 없는 ambiguous 줄은 추가 없이 임베딩 순서로 재정렬만. 유사도 하한은 메뉴 아닌 줄을 거르기 위해 두되, **값은 아직 정하지 않고 하한 0(로그만)으로 시작한다**. 일곱 개 모두 정답 후보 자신의 점수로 다시 센 하한 스윕(README 결과 3): 처음 메모의 "dev 값 약 0.91(e5-small int8)"은 다시 세도 맞았다(서비스 카탈로그에서 0.909면 정답이 상위 5개에 있는 45줄을 모두 남기고 정답 없는 26줄 중 5줄만 후보를 받음. 1순위 점수로 센 처음 값과 같음). 그러나 그 바 상품을 뺀 카탈로그에서는 0.910이 쓸모 있는 33줄 중 3줄을 잃으면서도 없는 술 300줄 중 119줄에 후보를 준다. 1단계 TF-IDF는 서비스 카탈로그에서 하한 0.380이면 43줄을 모두 남기고 정답 없는 26줄 중 8줄이 후보를 받지만, 상품을 뺀 카탈로그에서 0.380은 쓸모 있는 32줄 중 3줄 이상을 잃는다(29줄을 남기는 하한이 0.371). 하한은 dev 값이고 모델마다 척도가 다르므로(TF-IDF 0.38, e5 0.91, bge-m3 0.62) 서버 로그(`embeddingSimilarity`)와 I3 확인 뒤 정한다. **임베딩 단독 확인 권장은 달지 않는다.**
5. **LLM 층과의 관계: M3a 뒤에 둔다.** M3a가 confirm/추가를 끝낸 뒤 여전히 unmatched인 줄만 임베딩으로 채운다(확인 권장 영향 0). 권장 정책(위 4)을 M3a 결과에 그대로 적용하면 M3a가 남긴 ambiguous 줄도 임베딩 순서로 재정렬된다. 서비스 카탈로그에서는 보이는 목록 @1이 0.91 → 0.94(e5-small int8; TF-IDF 0.90 → 0.92)로 오르고, 생성 별칭이 없는 카탈로그에서만 0.83 → 0.81로 내린다. 서비스는 생성 별칭을 쓰므로 권장 정책은 그대로 두고, I3 확인 때 이 점도 함께 본다. E10 tools를 채택하면 `search_catalog`의 단어 겹침 대신(또는 함께) 같은 인덱스를 쓰는 것이 자연스럽다(측정은 Gemini 호출이 필요해 하지 않음).

### P40 서버 단계 어댑터 제안 (해울 담당, 모양만 제안)

```python
# app/adapters/embedding.py
class EmbeddingProvider(Protocol):
    model_id: str                      # "intfloat/multilingual-e5-small@614241f6:int8" (evidence와 캐시 키)
    dimension: int
    def embed(self, texts: Sequence[str]) -> np.ndarray: ...   # (n, d), L2 정규화, 실패 시 예외

class TfidfEmbeddingProvider:  # 1단계: 문자 1~3-gram, 인덱스를 만들 때 그 카탈로그 텍스트로 fit (fit(docs) 추가), 희소 벡터
class OnnxEmbeddingProvider:  # 2단계: onnxruntime, mean pooling, "query: " 접두어, intra_op_threads=설정값
class FakeEmbeddingProvider:  # 테스트: 문자 빈도 벡터 등 결정적, 네트워크·파일 없음

# app/matching/embedding_index.py
class EmbeddingIndex:
    def __init__(self, provider, entries: list[tuple[str, UUID]]): ...   # (별칭 원문 또는 표시명, product_id)
    def search(self, names: list[str], top_n: int = 10) -> list[list[tuple[UUID, float, str]]]: ...
    catalog_version: str     # 별칭/상품 테이블의 max(updated_at)+count 등
```

- **갱신**: 앱 시작 시 `CatalogSnapshot`의 활성 상품·별칭으로 인덱스 생성(TF-IDF fit 1초 미만 추정, e5 int8은 이 CPU에서 텍스트 5,382개 10.3 s로 백그라운드). 매칭 직전 `catalog_version`이 다르면 바뀐 텍스트만 다시 임베딩(텍스트→벡터 dict 캐시). 상품 승인·별칭 추가 API가 버전을 올린다. 모델 파일은 배포 때 고정 revision으로 내려받고 레포에 넣지 않는다.
- **연결 지점**: `_resolve_and_draft`에서 규칙 → (설정 시) M3a → `apply_embedding(results)` 순. 설정 `EMBEDDING_ENABLED`(기본 false), `EMBEDDING_MODEL`, `EMBEDDING_THREADS`, `EMBEDDING_MIN_SIMILARITY`. 실패(모델 없음, 예외)는 LLM 층처럼 로그만 남기고 규칙 결과 유지.
- **evidence** (`resolution_candidates`, method=`embedding`): `{"rule": "embedding", "embeddingSimilarity": 0.931, "matchedText": "글렌피딕 12년", "model": "<model_id>", "rerankedBy": "embedding"(재정렬만 한 규칙 후보에)}`. 확인 권장 키는 넣지 않는다. 문서 11장의 키 이름(`embeddingSimilarity`)을 따랐다.
- **테스트(가짜 임베더)**: ① 확정(exact_match/multi) 결과 불변 ② 새 결과는 항상 ambiguous, confirmRecommended 없음 ③ 후보 1개 ambiguous 줄엔 추가 없음 ④ 하한 아래면 unmatched 유지 ⑤ 카탈로그 버전 변경 시 새 별칭이 검색됨 ⑥ provider 예외 시 규칙 결과 그대로 ⑦ M3a 결과 뒤에 붙음. `ai/eval/test_p24_embedding_compare.py`가 ①~④의 오프라인 판이다.
- 계약 영향: `method="embedding"`은 이미 스키마·API에 있다. 새 evidence 키만 생기며 앱은 evidence를 그대로 보여주지 않으므로 FE 변경은 없을 것으로 본다(호진 확인 필요).

## 리뷰 반영 (#78 Codex, 2026-11-01)

- **TF-IDF 누출**: IDF를 모든 바·카탈로그 텍스트로 한 번에 fit해서, 다른 바 카탈로그에 별칭으로 들어 있는 그 바 자신의 메뉴 표기가 가중치에 섞였다. 이제 바 인덱스마다 그 인덱스 텍스트로만 fit한다(모델 임베더는 fit이 없어 영향 없음). 다시 돌린 TF-IDF: 서비스 `aliases` 임베딩 순위 @1/@5 0.71/0.96 → 0.67/0.97, 보이는 목록(권장 정책) 0.83/0.95 그대로, TF-IDF의 정책 조합 100개 모두 불변식 통과.
- **지연·메모리 라벨**: 표의 지연은 `all` 인덱스, 메모리는 실행 전체 값인데 "별칭 임베딩"으로 적었다. 라벨을 고쳤다(위 표 머리). 다시 돌린 하네스도 `all` 인덱스로 재므로 `aliases`만의 서버 인덱스 값은 여전히 재지 않았다.
- **하한 스윕**: 1순위 점수가 하한을 넘으면 정답 후보도 남는다고 셌다. 정답이 2~5순위면 정답 점수는 더 낮아 걸러질 수 있으므로 남는 정답을 부풀렸다. 이제 정답 후보 자신의 점수로 센다. 모델 6개를 다시 돌려 일곱 개 모두 스윕이 채워졌다. 정답을 전부 남기는 하한은 처음 값과 거의 같았고(e5-small int8 서비스 0.909 그대로, 상품 뺀 카탈로그 0.889 그대로), 일부만 남기는 하한이 내려갔다(예: e5-small int8 상품 뺀 카탈로그 90% 0.914 → 0.910, 없는 술 102 → 119줄; bge-m3 같은 곳 0.709 → 0.658, 44 → 89줄). 숫자 전체는 README 결과 3.
- **재현**: 처음 결과는 하네스가 커밋되기 전(`c976b4f` + 미커밋 하네스)에 돌아서 그 커밋으로 재현할 수 없었다. 이제 실행마다 커밋, 하네스·입력의 미커밋 변경, 하네스 SHA-256을 `provenance`에 남기고, 미커밋 변경이 있으면 `--allow-dirty` 없이는 돌지 않는다. TF-IDF는 `32b8314`에서, 그 뒤 일곱 개 모두 `8605400`에서 깨끗한 상태(`--allow-dirty` 없음)로 다시 돌렸다(결과 커밋은 그다음 커밋). 모델 6개의 recall·확인 권장 보정·M3a 조합·불변식과 처음부터 있던 정책 4종의 지표는 처음 값과 같았다. 새로 생긴 것은 정답 점수가 든 하한 스윕과 모든 모델의 `unmatched_k5+rerank_only` 정책이고, 바뀐 것은 지연·메모리·임베딩 시간(다른 CPU)뿐이다. TF-IDF도 지연 외에는 `32b8314` 값과 같다.
- **남은 일**: ① 운영과 같은 `t3.micro`(또는 늘린 `t3.small`)에서 API 프로세스와 함께 `aliases` 인덱스 하나의 메모리·지연 재기(TF-IDF 1단계 전, e5 2단계 전 각각). ② 하한과 1단계 TF-IDF 설정을 I3 동결 시험셋에서 고정 설정으로 한 번 확인.

## 리뷰 반영 2 (#78 두 번째 리뷰, 2026-11-01)

- **요약이 다른 입력의 결과를 섞음**: `summary`가 이제 모든 `model_*.json`의 카탈로그 파일·정답·라벨 SHA-256, 바별 카탈로그 digest, 카탈로그 변형·문서 집합·정책·M3a 정책, 하네스 SHA-256, 규칙 기준선이 같지 않으면 0이 아닌 코드로 멈춘다. 커밋은 비교하지 않고 `summary.json` `runs`에 남긴다(하네스·입력이 같은 다른 커밋은 같은 숫자를 낸다. 서버 매칭 코드는 해시하지 않으므로 그 차이는 규칙 기준선 비교로 잡는다).
- **모델 파일 해시**: `provenance.model`에 선언한 저장소·revision과 실제로 읽은 ONNX·`.onnx_data`·`tokenizer.json`의 SHA-256·크기를 남긴다.
- **M3a 뒤 임베딩의 recall**: 화면에 보이지 않는 후보까지 셌다(위 근거 표 아래 M3a 항목, 서비스 @5 0.98 → 0.97). 이제 결과마다 `candidates`로 센다.
- **M3a 조합의 정책**: `unmatched_k5`만 돌렸다. 권장 정책 `unmatched_k5+rerank_only`도 돌려 둘 다 남긴다. 부담·확인 권장은 같고 recall만 다르다(README 결과 3).
- **하한 스윕**: 첫 리뷰 지적(1순위 점수로 셈)은 `32b8314`에서 이미 고쳤다(`unmatched_top`이 정답 후보의 점수를 담음). 코드는 그대로다.
- 일곱 개를 모두 `bb526f8`에서 깨끗한 상태로 다시 돌렸다(결과 커밋은 그다음). M3a 조합의 recall과 지연·메모리 외의 숫자는 직전 실행과 같다. 추천은 바뀌지 않는다.
