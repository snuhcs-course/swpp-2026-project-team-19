## 추천

1. **모델: `intfloat/multilingual-e5-small`의 int8 ONNX export** (`onnx/model_qint8_avx512_vnni.onnx`, revision `614241f6`), onnxruntime + tokenizers + numpy, torch 없음. 품질은 fp32·bge-m3와 같고 지연·메모리는 가장 작다. 단 프로세스 RSS +450 MB는 현재 `t3.micro`(1 GiB)에 API와 함께 올리기엔 빠듯하다 → **서버를 `t3.small`(2 GiB) 이상으로 올리거나**, 그게 안 되면 **1단계는 TF-IDF**(추가 메모리 0, 보이는 목록 @5 0.95로 e5와 거의 같음, @1은 0.83 대 0.91)로 내고 서버 증설 후 e5로 바꾼다. 어댑터가 같으므로 교체 비용은 설정 한 줄이다.
2. **임베딩할 것: 상품 표시명 + 활성 별칭 원문 전부(생성 한글 표기 포함)**, 상품 점수는 최고값. 브랜드+연수 문자열은 생성 별칭이 있을 때 이득이 없어 뺀다(별칭이 없는 신규 상품을 위해 나중에 다시 볼 것).
3. **저장: 프로세스 메모리**. 텍스트 약 4,500개 × 384차원 float32 ≈ 7 MB, 전체 내적 1회 < 1 ms. pgvector는 RDS 확장·마이그레이션·백필이 필요한데 이 규모에선 얻는 것이 없다(상품 수만 개 이상이면 재검토).
4. **정책**: 규칙(+M3a)이 unmatched로 남긴 줄에만 상위 5개를 `method="embedding"`으로 붙이고, 확인 권장이 없는 ambiguous 줄은 추가 없이 임베딩 순서로 재정렬만. 유사도 하한은 메뉴 아닌 줄을 거르기 위해 두되, **값은 아직 정하지 않는다**. 처음 메모의 "dev 값 약 0.91(e5-small int8)"은 정답 후보가 아니라 1순위 점수로 하한을 고른 값이라 남는 정답을 부풀렸다(아래 "리뷰 반영"). e5는 정답 후보 점수로 다시 돌려야 하고, 그 전까지는 하한 0(로그만)으로 시작한다. TF-IDF는 다시 돌렸다: 서비스 카탈로그에서 하한 0.380이면 정답이 상위 5개에 있는 43줄을 모두 남기고 정답 없는 26줄 중 8줄이 후보를 받는다. **임베딩 단독 확인 권장은 달지 않는다.**
5. **LLM 층과의 관계: M3a 뒤에 둔다.** M3a가 confirm/추가를 끝낸 뒤 여전히 unmatched인 줄만 임베딩으로 채운다(확인 권장 영향 0). E10 tools를 채택하면 `search_catalog`의 단어 겹침 대신(또는 함께) 같은 인덱스를 쓰는 것이 자연스럽다(측정은 Gemini 호출이 필요해 하지 않음).

class OnnxEmbeddingProvider:  # onnxruntime, mean pooling, "query: " 접두어, intra_op_threads=설정값
class FakeEmbeddingProvider:  # 테스트: 문자 빈도 벡터 등 결정적, 네트워크·파일 없음

# app/matching/embedding_index.py
class EmbeddingIndex:
    def __init__(self, provider, entries: list[tuple[str, UUID]]): ...   # (별칭 원문 또는 표시명, product_id)

    catalog_version: str     # 별칭/상품 테이블의 max(updated_at)+count 등

- **갱신**: 앱 시작 시 `CatalogSnapshot`의 활성 상품·별칭으로 인덱스 생성(e5 int8 약 20 s, 백그라운드). 매칭 직전 `catalog_version`이 다르면 바뀐 텍스트만 다시 임베딩(텍스트→벡터 dict 캐시). 상품 승인·별칭 추가 API가 버전을 올린다. 모델 파일은 배포 때 고정 revision으로 내려받고 레포에 넣지 않는다.
- **연결 지점**: `_resolve_and_draft`에서 규칙 → (설정 시) M3a → `apply_embedding(results)` 순. 설정 `EMBEDDING_ENABLED`(기본 false), `EMBEDDING_MODEL`, `EMBEDDING_THREADS`, `EMBEDDING_MIN_SIMILARITY`. 실패(모델 없음, 예외)는 LLM 층처럼 로그만 남기고 규칙 결과 유지.
- **evidence** (`resolution_candidates`, method=`embedding`): `{"rule": "embedding", "embeddingSimilarity": 0.931, "matchedText": "글렌피딕 12년", "model": "<model_id>", "rerankedBy": "embedding"(재정렬만 한 규칙 후보에)}`. 확인 권장 키는 넣지 않는다. 문서 11장의 키 이름(`embeddingSimilarity`)을 따랐다.
- **테스트(가짜 임베더)**: ① 확정(exact_match/multi) 결과 불변 ② 새 결과는 항상 ambiguous, confirmRecommended 없음 ③ 후보 1개 ambiguous 줄엔 추가 없음 ④ 하한 아래면 unmatched 유지 ⑤ 카탈로그 버전 변경 시 새 별칭이 검색됨 ⑥ provider 예외 시 규칙 결과 그대로 ⑦ M3a 결과 뒤에 붙음. `ai/eval/test_p24_embedding_compare.py`가 ①~④의 오프라인 판이다.
- 계약 영향: `method="embedding"`은 이미 스키마·API에 있다. 새 evidence 키만 생기며 앱은 evidence를 그대로 보여주지 않으므로 FE 변경은 없을 것으로 본다(호진 확인 필요).

## 리뷰 반영 (#78 Codex, 2026-11-01)

- **TF-IDF 누출**: IDF를 모든 바·카탈로그 텍스트로 한 번에 fit해서, 다른 바 카탈로그에 별칭으로 들어 있는 그 바 자신의 메뉴 표기가 가중치에 섞였다. 이제 바 인덱스마다 그 인덱스 텍스트로만 fit한다(모델 임베더는 fit이 없어 영향 없음). 다시 돌린 TF-IDF: 서비스 `aliases` 임베딩 순위 @1/@5 0.71/0.96 → 0.67/0.97, 보이는 목록(권장 정책) 0.83/0.95 그대로, TF-IDF의 정책 조합 100개 모두 불변식 통과. 추천(1단계 TF-IDF 대안)은 바뀌지 않는다.
- **지연·메모리 라벨**: 표의 지연은 `all` 인덱스, 메모리는 실행 전체 값인데 "별칭 임베딩"으로 적었다. 라벨을 고쳤다(위 표 머리). 모델 파일을 이 환경에서 받을 수 없어 `aliases`로 다시 재지는 않았다.
- **하한 스윕**: 1순위 점수가 하한을 넘으면 정답 후보도 남는다고 셌다. 정답이 2~5순위면 정답 점수는 더 낮아 걸러질 수 있으므로 남는 정답을 부풀렸다. 이제 정답 후보 자신의 점수로 센다. 기록에 정답 점수가 없는 모델 결과(TF-IDF 외 6개)는 스윕을 `null`로 둔다.
- **재현**: 처음 결과는 하네스가 커밋되기 전(`c976b4f` + 미커밋 하네스)에 돌아서 그 커밋으로 재현할 수 없었다. 이제 실행마다 커밋, 하네스·입력의 미커밋 변경, 하네스 SHA-256을 `provenance`에 남기고, 미커밋 변경이 있으면 `--allow-dirty` 없이는 돌지 않는다. TF-IDF는 `32b8314`에서 깨끗한 상태로 다시 돌렸다.
- **남은 일**: 모델 6개(`minilm-l12`, `e5-small`, `e5-small-int8`, `e5-base`, `e5-base-int8`, `bge-m3`)는 Hugging Face에서 모델을 받을 수 있는 곳에서 현재 커밋으로 다시 돌려야 한다. 그래야 하한 스윕과 provenance가 생긴다(README의 재현 명령 그대로). recall·업주 부담·불변식 숫자는 하네스 수정과 무관하다(모델은 fit이 없고, 스윕은 요약 단계 계산).
