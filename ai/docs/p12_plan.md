# P12 (I2) 계획: CLOVA OCR 능력 확인 (사전 등록)

2026-10-14 · 박진우 (초안: Claude Code, 검토: 박진우)

이 문서는 **OCR·LLM 호출을 하기 전에** 커밋한다. 아래 지표와 판정 규칙은 결과를 보고 바꾸지 않는다. 바꿔야 하면 변경 이력에 이유와 시점(결과를 보기 전/후)을 적는다.

## 질문

1. CLOVA General OCR은 메뉴판의 이름·가격 글자를 얼마나 읽는가? (1단계: 읽기 상한)
2. OCR 줄 텍스트와 좌표를 텍스트 LLM으로 파싱하면 E1(Vision LLM)보다 항목 정답률이 나은가? (2단계)
3. (선택) 사진과 OCR 줄을 같이 Vision LLM에 주면 나아지는가? (하이브리드)

비교 기준 **E1** = P11 결과 `ai/runs/2026-10-13_test_v2_A2` (A2: `gemini-3.5-flash-lite` + thinking medium, 프롬프트 v2, 3회). test 항목 정답률 **0.843** (0.831–0.855), val 0.982.

## 데이터

- val: `eval/labels_v1.json` 9장 (위스키복춘·서로상). **파싱 프롬프트는 val에서만 고친다**
- test: `eval/labels_heldout_v1.json` 14장 (미라보·Beck·포레스트). 프롬프트 동결 커밋 뒤 **한 번만** 실행
- 사진은 `$BOTTLEMAP_DATA_DIR/eval_photos{,_test}`, EXIF 회전은 `extract.prepare_image`로 처리한 `prepared/` 파일을 그대로 OCR에 보낸다 (E1과 같은 바이트, 좌표도 같은 기준)
- 라벨은 SHA-256 고정(score.py), 수정하지 않는다

## OCR 호출

- CLOVA General OCR V2, JSON 본문, 이미지 base64, `lang: "ko"`. 헤더 `X-OCR-SECRET`
- **사진은 순차로 1장씩 호출한다** (CLOVA 동시 호출 제한). 병렬 호출 없음
- 장축이 8,000px 이상이면 장축 7,999px로 줄인 JPEG(q95, `<data_dir>/prepared_ocr/`)를 보낸다. 현재 val·test 23장은 장축 최대 4,032px라 해당 없음. 좌표는 보낸 이미지 기준
- 사진마다 `enableTableDetection` **false / true 두 버전**을 호출해 응답 원본을 `<data_dir>/ocr_cache/`에 저장. 콘솔에서 표 추출이 꺼져 있어(오류 0028) true 버전을 못 받으면 false만 쓰고 보고서에 적는다
- 캐시가 있으면 다시 호출하지 않는다. OCR은 사진당 버전별 1회
- 사진별·버전별 지연 시간(ms)과 호출 수를 `ai/runs/<날짜>_p12_clova/ocr_calls.json`에 기록 (키·URL은 기록하지 않음)

## 1단계 지표: 읽기 상한 (`ai/ocr/recall.py`)

OCR 결과에 정답 정보가 **글자로 존재하는지**만 본다 (위치·짝 대응은 보지 않음). 기본 입력은 표 인식 끈 버전의 `fields[].inferText`.

- **사진 텍스트 S:** 필드 텍스트를 응답 순서대로 정규화(score.py `normalize`: 소문자, 공백·문장부호 제거)해 이어 붙인 문자열
- **이름 토큰:** 라벨 `raw_name`을 공백·`/`·괄호로 나눠 정규화한 조각들. 한/영 병기(`A / B`)는 score.py `candidates`처럼 전체·각 부분을 후보로 보고, 후보 하나라도 조건을 만족하면 찾은 것
- **이름 재현율 (완전 일치):** 이름의 모든 토큰이 S의 부분 문자열인 정답 항목 비율
- **이름 재현율 (근사 일치):** 모든 토큰이 완전 일치하거나, 다음을 만족하는 비율
  - 토큰의 숫자 부분이 S에 그대로 있고
  - 숫자를 뺀 부분(3글자 이상일 때만)과 S의 어떤 부분 문자열의 편집거리 ≤ 1 (eval_plan 관대 일치와 같은 허용 폭). 숫자를 뺀 부분이 2글자 이하인 토큰은 완전 일치만 인정
- **보조: 한 줄 완전 일치:** 후보 이름 전체(정규화)가 복원된 한 줄 안에 들어 있는 비율. 브랜드 제목이 다른 줄에 있는 메뉴(미라보)는 구조상 낮게 나오므로 참고용
- **가격 재현율:** 가격이 채점 대상인 정답 항목(score.py `price_checked`)의 가격이 OCR 숫자 토큰으로 존재하는 비율. 같은 가격이 여러 번 나오면 개수까지 센다(다중집합 1:1 대응)
  - 숫자 토큰 = 필드 텍스트가 `₩`·`원`·`,`·`.`·`k`를 빼면 숫자뿐인 것 (`12년`, `700ml`, `46%`는 제외)
  - 값 v ≥ 1000이면 v원, v < 1000이면 v×1000 또는 v×10000 (약식 표기 "17", "1.6", "42.0")
- 집계: 사진별, 바별(항목 합산), 셋 전체(항목 합산). OCR은 1회라 범위 없음
- **E1 대조값:** 같은 계산을 E1 출력의 `raw_name`·`price_krw`를 텍스트로 보고 적용 (3회 평균). Vision LLM과 OCR의 "읽기"를 같은 자로 잰다

## 2단계: OCR + 텍스트 LLM 파싱 (`ai/ocr/parse.py`)

- 입력: 복원한 줄 텍스트 + 좌표(이미지 크기 기준 0–1000 정수 상자). 줄 복원은 `lineBreak`로 묶고, 한 줄 안에서 단어 사이 가로 간격이 큰 곳(줄 높이의 배수, `lines.py` 설정값)은 다른 열로 나눈다
- 모델: E1과 같은 `gemini-3.5-flash-lite`, thinking medium, 출력 스키마 E1과 동일(`MenuExtraction`). 이미지는 넣지 않는다
- 프롬프트: `ai/extract/` 가 아니라 `ai/ocr/ocr_parse_prompt_v1.md`. 추출 규칙은 가이드라인 v2.2(= 프롬프트 v2 규칙)를 따르고, 예시는 프롬프트 v2의 텍스트 예시만 쓴다. 평가셋 사진·라벨 내용은 넣지 않는다
- **val에서만 수정한다.** 수정 이력(무엇을 왜 바꿨고 val 점수가 어떻게 됐는지)은 `ai/runs/ai_usage_log.md`에 남긴다. 수정은 최대 5판(v1–v5)까지. 줄 복원 설정(열 나눔 간격, 표 인식 버전 사용 여부)도 val에서만 정하고 프롬프트와 함께 동결한다
- 반복: E1처럼 사진당 3회. 채점은 `ai/eval/score.py --set val|test` 그대로 (대표 지표: 항목 정답률, 3회 평균)
- 지연: 사진당 OCR 지연(1회) + LLM 지연(3회 평균). 호출 수: 사진당 OCR 1 + LLM 1

## (선택) 하이브리드

2단계 test 실행이 끝난 뒤에만 진행. 사진 + OCR 줄 텍스트를 같은 Vision LLM(A2)에 준다. 프롬프트는 E1 프롬프트 v2 + OCR 줄 사용 안내만 더하고 val에서 확인 후 동결, test 1회(3반복).

## 판정 규칙 (test, 실행 전 확정)

Δ = (CLOVA+LLM의 test 항목 정답률, 3회 평균) − (E1 0.843). 위에서부터 처음 해당하는 행을 적용한다. 0.03은 E1 3회 범위(0.831–0.855, 폭 0.024)보다 큰 차이만 의미 있게 보려는 기준이다.

| 결과 | 결정 |
| --- | --- |
| Δ ≥ +0.03 | OCR+LLM을 I3 추출 경로 후보로 올림. 지연·호출 수·비용을 같이 보고 담당자가 결정 |
| −0.03 < Δ < +0.03 | Vision LLM(E1) 유지. Beck_04 가격 정확도가 E1보다 높으면 CLOVA를 가격 행 검증 보조로 검토 |
| Δ ≤ −0.03 | Vision LLM 유지. OCR 경로는 리스크 R1 대응책에서 우선순위를 내림 |

하이브리드도 같은 규칙으로 E1과 비교해 따로 한 줄 적는다(실행했을 때만).

1단계 읽기 상한은 판정에 쓰지 않고 해석에만 쓴다. 이름 근사 재현율이 E1 대조값보다 낮으면 "OCR이 Vision LLM보다 덜 읽음"으로 적는다.
