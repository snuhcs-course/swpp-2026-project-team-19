# BottleMap Android 개발 작업 규칙 (`android.md`)

> 이 문서는 BottleMap Android 작업을 수행하는 AI Agent가 작업을 시작할 때 읽고 따라야 하는 프로젝트 공통 지침이다.
> 개별 작업 프롬프트에서 별도의 명시적 지시가 있으면 그 지시를 우선하되, 이 문서의 안전·권한 규칙(특히 PR 병합 금지와 작업 시간 보호)은 사용자가 명시적으로 변경하지 않는 한 계속 적용한다.

## 0. 작업 시작 시 반드시 확인할 것

1. 이 문서를 먼저 읽는다.
2. 사용자가 첨부한 관련 파일과 현재 대화의 작업 요청을 확인한다.
3. UI/UX 프로토타입(HTML/PDF/이미지/디자인 문서)이 첨부되어 있는지 확인한다.
4. 최신 Schedule Sheet와 관련 Task를 확인한다.
5. 저장소의 최신 `main`, 관련 작업 브랜치 및 열려 있는 PR의 상태를 확인한다.
6. 기존 구현과 의존성을 파악한 뒤, 재사용 가능한 구조를 우선 활용한다.

작업 요청에 필요한 첨부 파일이 현재 대화에 있거나 이전 작업에서 제공된 것으로 명시되어 있다면, 내용을 추측하지 않는다. 파일을 실제로 열어 확인한다. 파일을 찾을 수 없거나 접근할 수 없다면 그 사실을 먼저 밝히고, 확인 가능한 요구사항을 기준으로 진행하되 확인하지 못한 부분을 구현 완료로 주장하지 않는다.

---

## 1.0 수정 가능한 범위: Android 전용

- AI Agent가 직접 수정할 수 있는 대상은 **Android 앱 프로젝트에 속하는 코드와 Android 전용 설정·리소스·테스트**로 한정한다.
- Backend 코드, 서버 설정·배포 파일·DB 스키마·API 서버 테스트 등 Backend 관련 파일은 어떤 이유로도 수정하지 않는다.
- AI 모델·학습·추론·평가·데이터 파이프라인 등 AI 관련 코드와 설정도 수정하지 않는다. Android 앱에서 AI 기능을 호출하거나 표시하는 부분을 다루더라도 Android 프로젝트 바깥의 AI 구현 코드는 수정 대상이 아니다.
- Android 구현을 위해 Backend 또는 AI 측 변경이 필요해 보이면 직접 수행하지 않는다. 필요한 변경점, 근거, 영향 범위를 정리해 사용자에게 보고한다.
- 저장소에서 Android/Backend/AI 코드의 경계가 불명확하면 추측해서 수정하지 않는다. 파일 소유 영역과 빌드 모듈을 확인하고, 여전히 모호하면 사용자에게 확인한다.
- 커밋 전 변경 파일 목록을 확인한다. Android 범위 밖의 변경이 발견되면 해당 변경을 커밋에 포함하지 않는다.

## 1.1 UI 변경 사전 승인 및 시각적 확인

**화면의 UI/UX를 변경해야 한다면 구현 전에 반드시 사용자 확인을 받는다. 사용자 확인 없이 UI를 임의로 수정하지 않는다.**

- UI 변경에는 레이아웃, 화면 구성, 컴포넌트, 문구, 색상, 타이포그래피, 크기, 간격, 정렬, 아이콘, 이미지, 버튼, 입력 방식, 내비게이션, 화면 전환, 팝업, 애니메이션, 상태 표시 및 상호작용 변경이 포함된다.
- 첨부된 HTML/PDF/이미지 프로토타입은 먼저 열어 분석한다. 프로토타입이 있다는 사실은 UI 구현에 대한 사전 승인이 아니다.
- 현재 화면과 제안 화면의 차이를 사용자가 판단할 수 있도록 시각화 자료를 먼저 제공한다. 가능한 경우 실제 화면 크기와 비율에 가까운 목업·스크린샷·프로토타입 파일을 만들고, 파일 생성이 적절하지 않으면 대화창에 시각적 비교 자료를 제시한다.
- 시각화에는 변경 전/후, 변경 대상, 주요 인터랙션과 영향을 받는 화면을 식별할 수 있게 한다. 프로토타입이 제공된 경우 해당 프로토타입과 제안안을 비교할 수 있게 한다.
- 시각화 자료를 제시한 뒤 사용자의 명시적인 승인 또는 수정 지시를 기다린다. **승인 전에는 해당 UI 변경 코드를 작성·수정·적용하지 않는다.**
- 사용자가 승인하지 않은 시각적 세부사항을 임의로 보완하거나 승인 범위를 넘어 추가 UI 개선을 하지 않는다.
- 승인된 범위와 실제 구현 범위가 달라질 필요가 생기면 다시 시각화하고 확인을 받는다.
- UI 변경 승인은 Backend/AI 코드 수정 허가를 의미하지 않는다. Android 전용 수정 범위 규칙은 별도로 계속 적용한다.
- UI를 변경하지 않는 순수 로직·상태 관리·테스트 수정은 진행할 수 있다. 화면 동작이나 표시가 바뀔 가능성이 있으면 UI 영향 여부를 먼저 판단하고, UI 변경에 해당하면 승인을 받는다.

## 1. 기본 원칙 및 우선순위

### 1.1 사용자 요구와 UI/UX 프로토타입 우선

- 최신 사용자 요청과 사용자가 명시적으로 확정한 결정이 가장 우선한다.
- Android UI/UX를 설명하는 HTML 또는 PDF 프로토타입이 제공되었다면 반드시 먼저 확인한다.
- 프로토타입이 존재하는 화면은 사용자에게 시각화 자료를 제시하고 승인받은 범위에서 **프로토타입과 동일하게 구현**한다.
- 프로토타입이 있다는 사실은 UI 구현에 대한 사전 승인이 아니다. UI 변경 전 시각화 자료를 제시하고 사용자의 명시적 승인을 받아야 한다.
- 화면 구성뿐 아니라 문구, 요소의 순서, 색상, 타이포그래피, 크기, 간격, 정렬, 아이콘, 상태 표시, 입력 방식, 팝업, 애니메이션, 화면 전환 및 인터랙션을 함께 대조한다.
- HTML에 포함된 이벤트 핸들러와 상호작용이 있다면 실제 사용자 행동에 대응하는 Compose 동작으로 옮긴다.
- 프로토타입의 고정 예시 데이터는 화면 예시로만 취급한다. 실제 앱의 상품, 개수, 순서, 가격, 상태를 하드코딩하지 않는다.
- 최신 사용자 지시와 프로토타입이 충돌하면 최신 명시적 사용자 지시를 따른다. 충돌 사실과 적용한 기준을 기록한다.
- 프로토타입 파일이 없거나 읽을 수 없다면 확인하지 못한 레이아웃·동작을 임의로 만들어 프로토타입과 일치한다고 주장하지 않는다.

### 1.2 Backend 명세의 취급: Android 요구사항을 먼저 구현하고 명세를 후속 정렬

- Backend API 명세를 무조건적인 제품 요구사항 또는 Android UX의 최종 기준으로 취급하지 않는다.
- **Android UX 및 사용자 요구사항을 우선**하여 Android 내부 모델, Repository 인터페이스, ViewModel, 화면과 상태 흐름을 설계·구현할 수 있다.
- Backend 명세가 UX와 맞지 않거나 기능을 지원하지 못하면, Android 구현을 명세에 맞춰 축소하지 않는다. 먼저 Android 측에서 원하는 동작을 구현하고, 이후 필요한 API 계약 변경점·필드·엔드포인트·오류 처리·권한·데이터 생명주기를 정리해 Backend 명세와 협의한다.
- API가 준비되지 않은 기능은 Mock Repository 또는 Fake 구현체로 개발한다. UI와 ViewModel이 실제 서버 구현의 존재를 가정하지 않도록 경계를 분리한다.
- Android 내부 모델과 실제 Backend DTO를 구분한다. 내부 모델에 필요한 속성을 추가하는 것과 서버 계약을 확정하는 것을 혼동하지 않는다.
- **존재하지 않거나 합의되지 않은 API를 실제 서버 API인 것처럼 호출·문서화하지 않는다.** 실 API 연결이 필요한 시점에는 계약 공백과 필요한 Backend 변경을 명확히 표시하고 협의한다.
- 구현 후 Backend 명세를 보완해야 한다면 변경 제안과 근거를 정리한다. Backend 서버나 팀의 계약을 임의로 확정했다고 표현하지 않는다.
- Mock에서만 존재하는 값·상태·동작은 코드 주석과 문서에 `Mock only`, `TODO(Backend contract)` 등으로 식별한다.

### 1.3 기존 앱 보호

- 기존 Customer 검색, 검색 결과, 주변 매장, 지도/Kakao 지도, 바 상세, 로그인·로그아웃·Guest 흐름을 보존한다.
- Customer 기능을 대규모로 다시 작성하거나 불필요하게 리팩터링하지 않는다.
- Customer 동작에 영향이 있는 변경은 영향 범위와 회귀 테스트를 명시한다.
- 현재 앱의 기본 실행 경로는 **Customer 검색 화면**이다.
- 앱 첫 실행 시 Customer/Owner 모드 선택 화면을 노출하지 않는다.
- Owner 기능은 기존 앱에서 정해진 진입점(예: 마이페이지)을 통해 접근하도록 한다.
- Customer/Developer Flavor를 분리하는 이전 구조로 되돌리지 않는다. 단일 앱/단일 빌드 구성을 유지한다.

### 1.4 작은 변경과 기존 구조 재사용

- 작업 전에 현재 `main`과 대상 브랜치의 코드를 확인한다.
- 기존 Navigation, ViewModel, Repository, DTO/Mapper, UI 컴포넌트, 인증, Photo Picker, Camera, 영속성 구조를 조사한다.
- 이미 구현한 코드를 다시 만들지 않는다.
- 기존 구조로 요구사항을 충족할 수 있으면 그 구조를 확장한다.
- 요청하지 않은 대규모 아키텍처 변경, 광범위한 이름 변경, 무관한 포맷팅을 피한다.
- 수정 범위를 작고 검증 가능한 단위로 나눈다.

## 2. 반복 작업 사이클: 7단계

모든 기능 작업은 다음 7단계를 기준으로 진행한다. 각 단계의 상태와 검증 여부를 구분해 보고한다.

### 1단계 — Schedule 확인 및 작업 착수

작업을 시작할 때 최신 Project Schedule Sheet를 확인한다.

반드시 파악할 항목:

- 관련 Task ID
- Task 제목과 상세 설명
- Definition of Done / 완료 조건
- 선행 Task 및 의존성
- 현재 STATUS
- 기존 진행 상황과 비고

운영 규칙:

- 실제로 착수한 Task만 `Started`로 변경한다.
- 아직 착수하지 않은 Task는 임의로 시작 처리하지 않는다.
- 구현, 테스트, 실기기 QA, 리뷰 중인 Task는 완료 조건을 모두 만족하기 전까지 `Started`를 유지한다.
- Task 하나가 여러 PR에 걸쳐 있으면 해당 Task의 실제 DoD 전체를 기준으로 판단한다.
- PR 생성이나 코드 작성만으로 `Completed` 처리하지 않는다.
- **실제 작업 시간(work time)은 사용자가 직접 입력한다. AI Agent는 시간 필드를 절대 변경하지 않는다.**
- 완료일 등 시간 관련 필드도 명시적 요청 없이 임의로 변경하지 않는다.
- Schedule을 수정했다면 변경한 Task ID와 상태만 보고하고, 시간 필드를 건드리지 않았음을 확인한다.

### 2단계 — 기존 코드 분석 및 구현

구현 전에 최소한 다음을 확인한다.

1. 최신 `main`과 작업 브랜치의 차이
2. 관련 PR 및 미병합 변경사항
3. 관련 화면·Route·Navigation
4. ViewModel 및 상태 흐름
5. Repository 및 데이터 저장 구조
6. API 명세와 Backend 계약 공백
7. 첨부된 HTML/PDF UI 프로토타입
8. 관련 테스트와 현재 실패 상태

구현을 시작하기 전에 사용자에게 장황한 승인 절차를 만들 필요는 없다. 먼저 영향 범위를 간략히 정리한 뒤, 안전하게 진행 가능한 범위는 구현한다.

구현 계획에는 다음을 포함한다.

- 이번 작업의 Scope와 제외 범위
- 재사용할 코드
- 추가·수정할 파일
- 상태 및 데이터 흐름
- 선행 조건과 의존성
- 테스트 계획
- Definition of Done
- Backend 협의가 필요한 부분

### 3단계 — 자동 테스트 및 CI

기본 로컬 검증 명령:

```powershell
.\gradlew.bat :app:assembleDebug
.\gradlew.bat :app:testDebugUnitTest
.\gradlew.bat :app:lintDebug
```

필요에 따라 관련 테스트를 추가 실행한다. GitHub Actions의 Android CI와 AI CI도 시작하거나 상태를 확인한다.

실패 처리:

- 빌드·컴파일 오류는 원인을 파악해 수정한다.
- 테스트 실패는 원인을 파악하고 회귀 테스트를 보완한다.
- 새 버그를 수정하면 정상 사례뿐 아니라 오류·경계값·상태 복원 사례를 추가한다.
- 실행하지 않은 테스트를 통과했다고 보고하지 않는다.
- 로컬 실행 결과, GitHub Actions 결과, 사용자 실기기 결과를 서로 구분한다.

#### GitHub Actions CI를 기다리느라 구현 보고를 지연하지 않는다

- GitHub Actions CI는 실행 시간이 길어질 수 있으므로, 실행이 끝날 때까지 계속 대기하거나 반복 조회하지 않는다.
- 구현과 로컬에서 가능한 검증을 마친 뒤에는 **그 시점에 바로 사용자에게 결과를 보고한다.**
- GitHub Actions를 시작했다면 마지막으로 확인한 상태를 `queued`, `in_progress`, `success`, `failure` 등으로 정확히 표시한다.
- CI가 진행 중이면 `CI 진행 중 — 결과 미확인`으로 기록한다. 성공으로 간주하거나 통과라고 쓰지 않는다.
- CI 결과를 기다리는 동안 사용자를 붙잡아 두거나, 결과 확인을 위해 답변을 미루지 않는다.
- 이후 작업 또는 사용자가 결과 확인을 요청한 시점에 최신 CI 결과를 확인한다.
- 이미 실패 결과가 확인되었다면 그 실패를 숨기지 않고, 수정 가능한 문제는 해결한다.
- CI가 진행 중이라는 이유만으로 로컬 빌드·테스트 및 구현 결과 보고를 생략하지 않는다.

### 4단계 — Galaxy S23 실기기 검증

실기기 검증은 에뮬레이터가 아니라 USB로 연결한 실제 Galaxy S23을 기준으로 한다. 실기기 검증이 필요한 시점에는 다음 순서와 체크리스트를 반드시 함께 제공한다.

#### 4-1. 설치 전 Git 명령: 반드시 이 순서

실기기 검증 안내는 아래 네 단계를 **순서대로** 제공한다. `<branch-name>`은 실제 검증 대상 브랜치 이름으로 치환한다.

```powershell
git fetch origin
git switch <branch-name>
git pull --ff-only
.\gradlew.bat :app:installDebug "-PBOTTLEMAP_API_BASE_URL=https://bottlemap.o-r.kr/"
```

각 명령의 의미:

1. `git fetch origin` — 원격 브랜치와 최신 변경 정보를 가져온다.
2. `git switch <branch-name>` — 실제 검증할 작업 브랜치로 이동한다.
3. `git pull --ff-only` — 해당 브랜치의 최신 변경만 Fast-forward 방식으로 반영한다. 임의 Merge Commit을 만들지 않는다.
4. `installDebug` — Debug APK를 빌드하고 USB 연결된 Android 기기에 설치한다.

유의사항:

- `<branch-name>`을 실제 브랜치명으로 바꾸고, 사용자가 그대로 복사해 실행할 수 있게 제공한다.
- 브랜치가 로컬에 없으면 원격 브랜치 확인 후 적절한 추적 브랜치 생성 명령을 별도로 안내한다. 존재하지 않는 브랜치명을 추측하지 않는다.
- Git 명령은 반드시 위 순서로 안내한다. 설치 명령만 단독으로 먼저 제시하지 않는다.
- 기기에서 USB 디버깅이 허용되어 있고 `adb devices -l`에 `device`로 나타나는지 필요할 때 확인하도록 안내한다.
- 이 설치 방식은 Android Studio의 Run 버튼 대신 실제 기기에 설치하는 사용자의 표준 방식이다.
- 앱 데이터 초기화(`pm clear`)는 기본적으로 하지 않는다. Draft/사진 URI/로그인/프로세스 재시작 복원 검증이 목적이면 저장 데이터를 보존한다. 초기 상태 검증이 꼭 필요한 경우 데이터 삭제 범위와 영향을 먼저 경고한다.

#### 4-2. 실기기 검증 체크리스트 제공 방식

매 작업마다 해당 변경사항에 맞춘 구체적인 체크리스트를 만든다. 단순히 “정상 동작 확인”이라고 쓰지 말고, 사용자가 실제로 할 조작과 기대 결과를 적는다.

검증 범위는 필요한 항목을 선택한다.

- 기능의 정상 경로 및 주요 대체 경로
- 입력값, 유효성 검사, 저장 결과
- 화면 전환, Top App Bar Back, 시스템 Back/제스처
- 화면 재진입 및 매장/탭 전환
- 앱 백그라운드·완전 종료·재실행 후 상태 복원
- Photo Picker/카메라/URI 접근 및 선택 순서
- 키보드, IME, 포커스, 스크롤, 작은 화면, 큰 글꼴
- 세로 화면, 시스템 바 및 화면 잘림
- 오류·재시도·중복 탭·중복 제출
- 기존 Customer 검색·지도·바 상세·로그인 회귀

**체크리스트는 사용자가 직접 체크할 수 있고 한 번에 복사할 수 있는 형태로 제공한다.**

- 각 검증 항목은 개별 체크박스로 표시한다.
- 체크박스 상태를 사용자가 바꿀 수 있게 한다.
- 체크리스트 전체를 한 번에 복사하는 단일 `결과 복사` 버튼/기능을 제공한다.
- 복사 결과에는 모든 항목과 체크 상태가 포함되어야 한다. 예: `[x] 통과`, `[ ] 미확인`, 필요하면 `[!] 실패`와 메모.
- 체크 결과를 복사하면 사용자는 그 내용을 채팅에 그대로 붙여넣을 수 있어야 한다.
- 인터랙티브 체크박스/복사 버튼을 제공할 수 없는 환경에서는 동일한 형식의 Markdown 체크리스트와 복사하기 쉬운 하나의 텍스트 블록을 제공한다.
- 항목 수는 실제 검증 범위와 위험도에 맞춘다. 개수를 맞추기 위해 의미 없는 항목을 추가하지 않는다.
- 사용자가 결과를 제출하기 전에는 실기기 검증을 완료한 것으로 표시하지 않는다.

예시 형식:

```text
Galaxy S23 실기기 검증 결과
브랜치: feature/example
기기: Galaxy S23

[x] 1. 앱이 Customer 검색 화면으로 시작한다.
[x] 2. 변경한 화면에 정상 진입할 수 있다.
[ ] 3. 입력 후 저장하고 재진입해도 값이 유지된다.
[!] 4. 앱 완전 종료 후 Draft 복원이 실패한다.
    메모: 사진 선택 단계가 아니라 연락처 단계로 이동함.

결과: 2개 통과 / 1개 미확인 / 1개 실패
```

사용자가 복사한 결과를 전달하면 통과·실패·미확인을 구분해 정리하고, 실패는 원인 분석 및 수정 작업으로 연결한다.

### 5단계 — PR 작성 및 리뷰 준비

PR 제목과 본문에 관련 Schedule Task ID를 포함한다. PR에는 실제 변경과 검증 내용만 기록한다.

PR 본문 필수 항목:

| 항목 | 기록 내용 |
|---|---|
| Task ID | 관련 Schedule Task ID 및 작업명 |
| Scope | 이번 PR의 구현 범위와 제외 범위 |
| Implementation | 주요 설계 및 기능 변경 |
| Files | 핵심 수정·추가 파일과 이유 |
| Tests | 실제 실행한 빌드·JUnit·Lint·CI 결과 |
| Device QA | Galaxy S23 검증 상태 및 사용자 결과 |
| Limitations | 미완성 화면, 알려진 제약, 미검증 사항 |
| Backend | Mock 경계, 계약 공백, 후속 협의 항목 |

PR 운영:

- 작업이 진행 중이거나 필수 검증이 남아 있으면 Draft PR을 활용한다.
- 리뷰 요청이 가능한 상태가 되면 PR을 Ready for Review로 전환한다.
- 기존 PR에 계속 커밋할지 새 PR을 생성할지는 변경 범위·의존성·리뷰 가능성으로 판단한다.
- PR 설명은 새로운 커밋과 검증 상태에 맞춰 갱신한다.
- 사용자가 직접 수행한 실기기 테스트는 사용자 보고 결과임을 표시한다.
- CI가 진행 중이면 pending/in progress로 기록하고 통과로 표시하지 않는다.

### 6단계 — Codex Review 및 수정·재검증

최신 Codex Review 및 관련 댓글을 확인한다. 모든 지적을 무조건 반영하지 않고 아래 기준으로 분류한다.

#### Fix — 수정

- 실제 코드 버그
- 상태 불일치 또는 상태 전이 오류
- 데이터 유실·중복·무결성 문제
- 확정된 요구사항 또는 확정 API 명세 위반
- 빌드·컴파일·테스트 실패
- 보안상 명확하고 현재 구현 범위에서 해결 가능한 결함

기존 사용자 요구와 합의된 정책을 유지하며 안전하게 해결할 수 있는 문제는 별도 승인 없이 수정한다. 회귀 테스트를 추가하고 CI 및 필요한 실기기 재검증을 수행한다.

#### Defer — 보류

- 합의되지 않은 Backend 기능을 새로 구현하라는 제안
- 현재 Iteration 범위를 벗어나는 기능 확장
- 제품 동작에 영향이 없는 취향·스타일 수준의 리팩터링
- Mock 구현의 목적과 충돌하는 불필요한 실서버 의존성 추가

보류 사유와 후속 조건을 기록한다. Codex 지적이 0건이 될 때까지 무조건 수정하지 않는다.

#### Decision — 사용자·팀 확인

- Backend API 계약 또는 서버 동작 변경
- 인증·인가·보안 정책의 주요 변경
- 개인정보·사진의 저장·전송·삭제·보존 정책 결정
- 주요 UX 및 제품 정책 변경
- 데이터 마이그레이션이나 호환성에 중대한 영향을 주는 선택

임의로 결론내지 않는다. 근거, 선택지, 영향, 권장안을 사용자에게 보고하고 결정을 받는다.

#### 리뷰 반복 규칙

- 최신 리뷰의 대상 커밋과 지적 내용을 확인한다.
- 해결한 문제는 코드·테스트·PR 설명에 반영한다.
- 수정 후 최신 CI와 재리뷰를 확인하되, GitHub Actions가 오래 걸리면 계속 대기하지 않는다.
- CI나 리뷰가 진행 중이면 상태를 표시하고 구현 결과를 먼저 보고한다.
- 타당한 지적만 수정하고, 보류·팀 확인 항목은 이유를 PR 또는 작업 기록에 남긴다.

### 7단계 — 최종 검증 및 완료 판단

- 요청 기능의 DoD가 실제로 충족됐는지 확인한다.
- 수정이 필요한 Codex 지적이 남아 있는지 확인한다.
- 필요한 재검증 결과를 확인한다.
- PR의 최종 상태와 병합 여부에 대한 사용자 판단을 확인한다.
- 실제로 검증하지 않은 항목은 미확인으로 남긴다.
- Schedule을 완료 기준에 맞게 업데이트한다.

#### PR 병합 권한 — 반드시 지킬 것

**사용자가 명시적으로 Merge를 요청하지 않는 한 어떤 PR도 임의로 병합하지 않는다.**

- CI, 테스트, 실기기 검증, Codex Review가 모두 통과해도 자동 병합하지 않는다.
- GitHub의 Merge 버튼, 자동 병합 설정, squash merge 등을 사용자 승인 없이 실행하지 않는다.
- 병합 준비·권장 여부는 판단해 보고할 수 있지만, 실제 병합은 사용자 명시적 요청이 있어야 한다.
- 코드 수정, 커밋, PR 생성·업데이트, Ready 전환, 리뷰 대응은 이 규칙에 위배되지 않는 범위에서 진행할 수 있다.

#### Schedule Completed 기준

- 해당 Task의 실제 요구사항과 DoD를 모두 충족해야 한다.
- 위 7단계의 필요한 작업과 검증이 끝나야 한다.
- 필수 리뷰 수정, 실기기 재검증 또는 최종 PR 처분 결정이 남아 있다면 `Started`를 유지한다.
- 실제 작업 시간과 사용자가 직접 관리하는 시간 필드는 절대 수정하지 않는다.
- PR 병합이 Task DoD에 포함되어 있다면, 사용자의 병합 요청 및 실제 병합 전에는 `Completed` 처리하지 않는다.
- Task가 병합 없이도 완료될 수 있는 범위인지 불명확하면 임의로 완료 처리하지 말고 판단 근거를 보고한다.

## 4. 구현 및 검증 결과 보고 형식

구현을 끝낸 시점에 보고한다. GitHub Actions가 진행 중이면 결과를 기다리지 않는다.

보고에는 다음을 포함한다.

1. 관련 Task ID와 현재 Schedule 상태
2. 구현한 기능 및 변경 범위
3. 핵심 변경 파일
4. 실제 실행한 로컬 빌드·테스트 결과
5. GitHub Actions Android CI / AI CI의 마지막 확인 상태
6. 실기기 검증이 필요하면 위의 Git 명령 4단계와 일괄 복사 가능한 체크리스트
7. PR 번호·브랜치·커밋·현재 상태(존재하는 경우)
8. Codex Review 상태와 Fix/Defer/Decision 분류(확인한 경우)
9. 미완성 기능, Backend 협의 항목, 미검증 사항
10. 다음에 필요한 사용자 행동(예: Galaxy S23 체크리스트 수행, 정책 결정, Merge 요청)

상태 표현 예:

- `구현 완료` — 코드 변경 작업이 끝났음
- `로컬 테스트 통과` — 명시한 로컬 명령이 실제로 성공했음
- `GitHub CI 진행 중` — 완료를 기다리지 않고 마지막 확인 상태를 표시함
- `실기기 검증 대기` — 사용자의 Galaxy S23 검증이 필요함
- `실기기 검증 통과` — 사용자가 결과를 전달했고 항목을 확인했음
- `Codex Review 진행 중` — 최신 리뷰 결과를 아직 확인하지 못했음
- `PR 미병합` — 사용자가 병합을 요청하지 않았음

구현이 완료됐지만 CI가 진행 중이라는 이유로 답변을 지연하지 않는다. 반대로 pending인 CI를 성공했다고 보고하지도 않는다.

## 5. 프로젝트 기본 기술·제품 기준

현재 대화와 기존 구현에서 확립된 기준을 따른다. 더 최신 사용자 지시가 있으면 갱신한다.

- Android 단일 앱 구조를 유지한다. Customer/Developer Flavor로 되돌리지 않는다.
- 앱 최초 실행은 Customer 검색 화면이다. Customer/Owner 모드 선택 화면을 띄우지 않는다.
- Owner 진입은 기존 Customer 앱의 진입점에서 수행한다.
- 기존 Customer 검색·지도·바 상세·인증 기능을 보호한다.
- Owner UI의 기준은 가장 최신에 제공된 사용자 승인 HTML/PDF 프로토타입이다.
- 프로토타입 예시 데이터, 개수, 순서, 상품, 가격을 실제 비즈니스 로직에 하드코딩하지 않는다.
- 사진 메뉴 등록은 사진별 추출 결과, 동적 줄 수와 후보 수, `extractedItemId`, `productId`, 검수 결정 및 게시 결과를 데이터로부터 구성한다.
- 작업 ID와 검수 버전 등 서버 작업의 식별·복구 정보를 보존한다. 큰 이미지 바이트나 대형 응답 객체를 부적절하게 SavedState에 저장하지 않는다.
- 저장된 Draft와 Photo URI의 재진입·재시작 복구를 고려한다.
- Loading, Empty, Error/Retry, Saving, Success를 명시적으로 처리한다.
- 신청 상태, 메뉴 Import 상태, 게시 가능 상태, 영업 상태를 하나의 `status`로 뭉뚱그리지 않는다.
- 기존 메뉴 변경과 신규 메뉴 추가를 혼동하지 않는다. 추가 전용 정책은 Android UI뿐 아니라 Mock Repository에서도 보호하고, 실제 서버 반영 전 Backend 보장 여부를 확인한다.
- 사진 원본, 신청 첨부, 고객 공개 사진, 메뉴판 AI 검수 이미지는 사용 목적과 보존·접근 권한을 구분한다.
- Portrait-only 정책을 유지하고 시스템 바, 키보드, 작은 화면, 큰 글꼴, 시스템 Back을 검증한다.
- Debug 전용 Fixture·도구·테스트 진입점은 Release 사용자에게 노출되지 않도록 분리한다.

## 6. 실기기 QA 결과를 받았을 때의 처리

사용자가 체크리스트 결과를 복사해 보내면 다음 순서로 처리한다.

1. `[x]` 통과, `[ ]` 미확인, `[!]` 실패를 구분한다.
2. 실패 항목의 재현 절차와 기대 결과·실제 결과를 정리한다.
3. 기존 코드와 관련 상태 저장·Navigation·Lifecycle 로직을 확인한다.
4. 기존 요구 범위 안의 버그는 추가 승인 없이 수정한다.
5. 회귀 테스트를 추가하고 로컬 검증을 실행한다.
6. GitHub CI를 시작·확인하되 완료까지 기다리지 않고 진행 상황을 보고한다.
7. 수정된 기능만 대상으로 하는 최소 실기기 재검증 체크리스트를 제공한다.
8. 사용자의 재검증 결과를 받은 뒤 PR 및 Schedule 상태를 갱신한다.

실패를 해결하는 과정에서 Backend 계약, 인증·보안, 주요 제품 정책이 바뀌어야 한다면 먼저 Decision으로 분류해 보고한다.

## 7. 완료 전 최종 점검표

각 작업 종료 시 아래 항목을 확인한다.

- [ ] 수정 대상이 Android 앱 코드·설정·리소스·테스트 범위인지 확인했다.
- [ ] Backend 코드·설정·DB·테스트를 수정하지 않았다.
- [ ] AI 모델·학습·추론·평가·데이터 파이프라인 코드를 수정하지 않았다.
- [ ] UI 변경이 필요하면 구현 전에 시각화 자료를 사용자에게 제시했다.
- [ ] UI 변경에 대한 사용자의 명시적 승인을 받기 전에는 UI 코드를 수정하지 않았다.
- [ ] 최신 Schedule의 Task ID·설명·의존성·상태를 확인했다.
- [ ] 실제 착수한 Task만 `Started`로 변경했다.
- [ ] 사용자가 제공한 첨부 파일을 먼저 확인했다.
- [ ] HTML/PDF UI 프로토타입이 있으면 화면과 동작을 기준으로 구현·대조했다.
- [ ] 기존 Android 코드와 Customer 기능을 보호했다.
- [ ] Backend 명세를 맹신하지 않고 Android UX 요구사항을 우선했다.
- [ ] 미합의 서버 기능은 Mock으로 분리했고 API를 지어내지 않았다.
- [ ] 로컬에서 실행한 빌드·테스트 결과를 사실대로 기록했다.
- [ ] GitHub Actions가 진행 중이면 기다리지 않고 그 상태를 표시했다.
- [ ] 실기기 검증 시 `fetch → switch → pull --ff-only → installDebug` 순서로 명령을 제공했다.
- [ ] 실기기 체크리스트에 개별 체크박스와 전체 결과 복사 기능을 제공했다.
- [ ] 사용자가 보고하지 않은 실기기 결과를 통과로 기록하지 않았다.
- [ ] PR에 Task ID, Scope, 변경 파일, 테스트, Device QA, Limitations, Backend 항목을 기록했다.
- [ ] Codex 지적을 Fix / Defer / Decision으로 구분했다.
- [ ] 해결 가능한 Fix는 수정·회귀 테스트·재검증했다.
- [ ] Defer 및 Decision의 이유와 후속 조건을 기록했다.
- [ ] 사용자의 명시적 요청 없이 PR을 Merge하지 않았다.
- [ ] 실제 작업 시간 필드를 변경하지 않았다.
- [ ] 해당 Task의 전체 DoD를 충족하기 전에는 `Completed`로 변경하지 않았다.
- [ ] 미완성·미검증·CI pending 항목을 명확히 남겼다.

**핵심 규칙:** Android 프로젝트 밖의 Backend 및 AI 코드는 절대 수정하지 않는다. UI 변경은 시각화 자료로 먼저 사용자 확인을 받고 명시적으로 승인된 범위만 구현한다. 첨부된 최신 UI/UX 기준과 사용자 요구사항에 맞춰 Android를 먼저 구현한다. 기존 앱을 보호하고, Backend 공백은 Mock으로 격리한 뒤 명세를 후속 정렬한다. 자동 검증과 실기기 검증을 구분하고, CI를 기다리느라 구현 보고를 지연하지 않는다. Codex는 타당성에 따라 선별 대응한다. 실제 기기 검증은 사용자가 수행하며, PR 병합은 사용자의 명시적 요청이 있을 때만 한다.
